# Analytics / Dashboard Loading Audit

**Scope:** `src/app/(dashboard)/analytics/` (page + 8 components), `src/app/(dashboard)/dashboard/page.tsx`, all `/api/dashboard/*` routes, i18n, build output.

**Headline:** No P0 crashes or blank pages. Every analytics component implements loading + error + empty states and guards null data. The subsystem is **load-safe**. Findings are P1/P2 quality/i18n/perf issues.

---

## Dimension 1 — Component Mount Safety: **WARN**

All 6 *rendered* components (`LeadHealth`, `SalesLoad`, `PipelineFunnel`, `PaymentTracker`, `AdsROI`, `WeeklyTrends`) have loading + error + empty branches, and every `fetch()` is caught (try/catch or `.catch`). No component derefs nested data before null-guarding. **No crashes on null/undefined.**

- **P1 — `AdsROI.tsx:104` dead branch.** `if (error === "forbidden")` compares against the literal string `"forbidden"`, but the 403 path sets `setError(t("common.forbidden"))` (line 81, a *translated* string). The guard never matches, so the intended "render nothing for 403" falls through to the red error block (line 108) instead. Low real-world impact (component only mounts in the management view, where 403 won't fire), but it's incorrect edge-state handling.
- **P1 — no `res.ok` check before `.json()`.** `LeadHealth.tsx:306-307` and `SalesLoad.tsx:312-313` do `.then((r) => r.json()).then((d) => { if (d.error) throw … })`. A non-JSON 5xx (gateway/HTML) makes `r.json()` throw a `SyntaxError` that surfaces to the user as a raw parse message.
- **P2 — raw server messages to user.** `LeadHealth.tsx:332` (`Failed to load: {error}`) and `SalesLoad.tsx:336` expose `e.message` verbatim — minor info-disclosure.
- **P2 — nested component anti-pattern.** `PaymentTracker.tsx:96-164` defines `STATUS_CONFIG` and the `StatusBadge` component *inside* the render body → recreated/remounted every render. Not a crash, but loses DOM state and thrashes on re-render.
- **P2 — orphaned components.** `LeadSources.tsx` and `TeamPerformance.tsx` are **not imported by `analytics/page.tsx`** (page only uses 6 of 8). They're built but never rendered — dead code.

## Dimension 2 — API Route Health: **PASS (one WARN)**

Every `/api/dashboard/*` route is wrapped in `try/catch` returning `{ error }` + HTTP 500, returns 401 JSON on auth failure, and handles empty result sets (reduces over `[]`, defaults to 0). `ads-roi` returns 403 for non-CEO/admin. **No route throws an unhandled exception in the common path.**

- **P2 — auth/role outside try/catch.** `lead-health/route.ts:5-26` and `sales-load/route.ts:5-22` place `createServerSupabase()` + `auth.getUser()` + `profiles` fetch *before* `try`. If `createServerSupabase()` throws, it's unhandled → Next default 500 (not the route's clean JSON). Edge case, but inconsistent with `pipeline-funnel`/`payment-tracker`/`weekly-trends`/`ads-roi` which wrap everything.
- **P2 — invalid PostgREST filter, silently swallowed.** `pipeline-funnel/route.ts:178` does `.eq("lead_id", supabase.rpc("get_user_leads_ids", { p_user_id }))` — passing an RPC *builder* as a filter value is invalid. The result error is unchecked (line 180 `const { data: events } = …`), so `lostFromStage` stays `{}` for sales users and **"Where I lose Most" never populates**. Silent data gap, not a crash.

## Dimension 3 — Data Dependency Chains: **WARN**

- **Good:** the 6 components fire their APIs in parallel (independent mounts), so there's **no app-level waterfall** across widgets. Nested-data null-checks are present (`data?.stages`, `summary && …`, `weeks.length === 0` early-return).
- **P2 perf — redundant in-component role waterfall.** `PipelineFunnel.tsx:162-190` and `PaymentTracker.tsx:104-133` each run a sequential `getUser() → profiles → (wait) → data fetch`. `LeadHealth` does the same via `useUserRole.ts:20-44`. The data API already resolves role server-side, so the client pre-fetch only adds a round-trip and gates the data call. On mount this is ~6×(auth+profile) calls before any data loads.
- **P2 — triplicated role fetch on the page.** `analytics/page.tsx:21-37` fetches role itself **and** `useRequireRole` (`useRequireRole.ts:23-60`) fetches it again = up to 3-4 parallel role lookups for one page.
- **i18n — Arabic is not a supported locale at all.** `translations.ts` has only `en` (line 3) and `zh` (line 1277); `LanguageContext.tsx:35` toggles hardcoded `en ↔ zh`. There is no `ar`, no RTL. So "breaks in Arabic" is **N/A** — Arabic was never wired up. *ZH* gaps do exist: `LeadHealth.tsx` hardcodes English ("📊 Lead Health", "Total Leads", "Active", "Dormant", "Zero Follow-up", "+N this week", "leads", "My Overdue Follow-ups", the `prompt`/`alert` text, "Failed to load:", "Quality Distribution" at line 127); `dashboard/page.tsx:1104` has `{s.total} leads · {s.won} won · {convRate}%` with no ZH variant (the Team-Ownership table at 961-972 uses inline `language === "zh" ? … : …` ternaries instead of `t()`).

## Dimension 5 — Performance / UX: **WARN**

- **Loading indicators:** all present (text spinners or pulse skeletons). ✓
- **Error states:** all show a message (though raw in 2 components). ✓
- **Empty states — two gaps:**
  - **P2** `SalesLoad.tsx` CEO rep table renders an empty `<tbody>` with no empty-state row when `repStats` is `[]` (unlike every other table in the page).
  - **P2** `WeeklyTrends.tsx:133` guards on `data.weeks.length === 0`, but the API *always* returns 12 weeks (even all-zero), so `noWeeklyData` effectively never renders — users see an empty chart of zeros instead of a "no data" message on a fresh install.
- **P2 — no per-route boundary.** The analytics route has no own `error.tsx`/`loading.tsx` (only the group-level ones at `src/app/(dashboard)/`). Since the page is a client component doing its own fetches, the route `loading.tsx` wouldn't help those anyway, and render crashes are caught by the group `error.tsx` — acceptable, but a render-level throw still relies on the shared boundary.
