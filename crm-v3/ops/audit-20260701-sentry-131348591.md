### 3.3 fingerprint 复用风险评估

**判断：未来不会被复用为生产告警指纹，原因是：**

1. `SentryTestError` 是个**自定义 Error class**，定义来源只在 T1-12 当时的验证 throw 语句里。
2. T1-12 已经在 TASKBOARD 标记 ✅ Done（`TASKBOARD.md:42`），**不会再有人为 throw**——生产代码里也没有任何主动 throw `SentryTestError` 的位置（grep 验证：`search_files content "SentryTestError"` 在 `/home/ubuntu/newme-platform` 全仓无代码引用，仅出现在本审计上下文和 TASKBOARD）。
3. Sentry fingerprint 算法基于 `exception.type + stacktrace frames` + 用户注入的 `fingerprint` 配置——若将来 production 真出现同名的 `SentryTestError`，指纹本身确实可能一致（这是 Sentry 默认行为）；但 production 代码本身没有定义 `SentryTestError`，**等价于"指纹保留但触发器不再存在"，安全**。
4. Sentry issue 被 `archived_forever` 后，**再次出现的同指纹事件也不会自动 un-archive**——这是一个隐性副作用（见 §3.5）。

### 3.4 比"archived_forever"更优的方案

| 方案 | 优 | 劣 | 推荐度 |
|------|----|----|------|
| **A. resolve in next release**（当前实际是用 archived_forever，但是更轻量） | 干净，issue 从 active 列表消失 | 仍可能被同指纹复用触发 | ⭐⭐⭐ |
| **B. ignore until_escalating**（推荐改这个） | 24 小时无新增自动恢复忽略 | 配置略复杂 | ⭐⭐⭐⭐ |
| **C. delete**（不存在） | — | Sentry API 无此操作 | ❌ |
| **D. keep unresolved + silence alert rule**（治标） | issue 保留 | alert 规则失效 | ❌ |

**结论**：理想的"事后补正"方案是把 substatus 从 `archived_forever` 降级到 `until_escalating`（若可行），或至少加 issue comment 标注缘由。**这要下次补操作时同步做（详见 §6）。**

### 3.5 隐性副作用清单

- Sentry issue archived_forever **不是不可逆**——可在 Sentry UI 或 API 反向 `PUT status=unresolved`。
- 但**反向操作不会自动恢复告警规则**——若重开 issue，需手动重连 alert。
- archived issue 仍出现在 Sentry 项目"Archived"标签下，仍然可查证，**不是真删除**。

## 7. 下次规则建议 — 运维操作边界定义（精简版）

如下表，把所有运维操作做分类，给出 Hermes 单审、双审、或免审的判别。

| 类别 | 操作 | 档位 | 备注 |
|------|------|------|------|
| **监控/查询（只读）** | Sentry issue 列表 GET、journalctl 查询、nginx access 日志、PostHog session 查询、Supabase service_role SELECT | 🟢 免审 | 不可逆变更 = 0 |
| **Sentry（状态改动）** | resolve issue | 🟡 单审 | 保留可见、回到 history |
| **Sentry（高级别）** | ignore / archived_forever / 删除 / merge | 🔴 双审 | 改变告警拓扑 |
| **服务（轻）** | systemctl restart、nginx reload、`npm run deploy`（脚本化部署） | 🟡 单审 | 可回滚 |
| **服务（重）** | 升级 Node 版本、修改 systemd unit 文件（新增/删除 Environment）、改 nginx 站点配置 | 🔴 双审 | 影响开机/重启行为 |
| **数据库（DDL）** | 任何 migration（CREATE TABLE / ALTER / DROP） | 🔴 双审 | 表结构变更是核心 |
| **数据库（DML 临时）** | 单行 UPDATE / INSERT 修数据（生产） | 🔴 双审 | 哪怕一行，避免野操作 |
| **数据库（DML 批量）** | UPDATE/DELETE 多行（任何生产数据） | 🔴 双审 + 备份 | 影响不可逆 |
| **Secrets & .env** | 任何 token 轮换、密钥新增/删除、环境变量改值 | 🔴 双审 | 影响认证 |
| **生产 debug** | 临时加 console.log、加 Sentry.setTag 排查 | 🟡 单审 | 需当日清理 |

> 决策依据：**可逆性 + 影响半径 + 操作类型持久度**。不可逆 → 🔴；可逆但有副作用 → 🟡；纯查询 → 🟢。
