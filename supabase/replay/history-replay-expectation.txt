# Expected result of MODE=history — the recorded shape of the migration debt.
#
# `MODE=history bash scripts/replay-migrations.sh` applies every 14-digit
# migration in supabase/migrations/ to an empty database, in order, one
# transaction per file, exactly as the Supabase CLI would. It does not pass. That
# is the finding, and this file is how it is gated instead of narrated.
#
# The previous revision of this branch ran that mode inside the green CI job with
# continue-on-error: true. A step that cannot fail the job is not a check, and it
# meant the job reported success while reporting, in its own log, that the
# migration directory does not replay. The step is now gated on the values below:
# the run must stop at EXACTLY this file after EXACTLY this many successful
# applications. Better and worse both fail.
#
#   * If someone repairs a migration, the count moves and this job goes red until
#     these numbers are updated — which forces the repair to be acknowledged
#     rather than absorbed.
#   * If someone lands a change that breaks an EARLIER migration, the count drops
#     and the job goes red immediately. Under continue-on-error that regression
#     was invisible.
#
# Current stop: 20260602010000_crm_mvp_final.sql line 125 recreates the
# lead_alerts view selecting l.rep_name, a leads column that no migration in the
# directory creates. Production has the column because it was added by hand. The
# file therefore rolls back in full (one transaction per file) and the replay
# cannot continue.
#
# Why the fix is not in this branch: repairing the history needs the live schema
# to decide what each dead file should now say, and several of the dead files
# carry backfill UPDATEs that would rewrite production rows the first time they
# were allowed to run. The correct repair is `supabase db dump` squashed into a
# baseline, taken by an operator who holds production credentials. That is
# recorded as an open item on TASKBOARD.md and is NOT claimed as done here.
#
# Note also what these numbers cost: 20260806000000_baseline_undeclared_production
# _objects.sql declares the missing objects, and dated at the end of history — as
# forward-only requires — it applies far too late to help this replay. An earlier
# revision backdated it to 20260601010000 so that the replay got further (9 files
# instead of 2). That improvement was a history rewrite and was withdrawn. The
# smaller number here is the honest one.
#
# Update procedure: re-run the mode, read the log, and change these two values in
# the same commit as whatever moved them, with the reason in the commit message.

EXPECTED_APPLIED=2
EXPECTED_STOPPED_AT=20260602010000_crm_mvp_final.sql
