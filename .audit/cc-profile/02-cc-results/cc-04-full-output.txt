# API Route Security Audit — `newme-platform` (71 routes)

**Auth taxonomy in this codebase** (no shared auth library — logic is inline per route):
- `createServerSupabase()` (`@/lib/supabase-server`) → user-auth SSR client, **RLS applies**
- `supabaseAdmin` (`@/lib/supabase-admin`) or inline `createClient(url, SUPABASE_SERVICE_ROLE_KEY)` → **service_role, bypasses RLS**

✅ = I read the file directly. 👁 = reported by parallel audit agent, corroborated by the `service-role-grep` artifact + line citations.

---

## P0 — Auth bypass / IDOR / credential disclosure (blocks production)

**[P0] `/api/cos/download-url` — IDOR: any authenticated user can mint a signed URL for ANY stored file** ✅
File: `src/app/api/cos/download-url/route.ts:10-58`
Risk: Only checks a path-prefix regex (`quotations/|attachments/|leads/|media/|contracts/`, line 29). No ownership check. A `sales` user requests `key: "contracts/<peer's contract>.pdf"` and gets a presigned download URL → every quote, attachment, signed contract in COS is readable by any logged-in user. Also passes `env: { ...process.env }` to the `python3` subprocess (line 42), leaking `SUPABASE_SERVICE_ROLE_KEY`.
Fix: Resolve the lead/contract owner from the key prefix and require `assigned_to/sales_id === user.id` or management; pass a minimal env to `execFile`.

**[P0] `/api/monitoring/report` — fully unauthenticated; writes attacker-controlled data to disk** ✅
File: `src/app/api/monitoring/report/route.ts:22-56`
Risk: No `getUser()`, no secret, no rate limit. Accepts arbitrary `{message,stack,type,url,userAgent}` and `fs.appendFileSync`s it to `/tmp/hermes/errors/<md5>.jsonl`. Unauthenticated disk-fill / log-injection / DoS. (Note: filename is MD5-hex → not a path-traversal; the real issue is unbounded unauth writes + stored-XSS if logs render in admin UI.)
Fix: Require auth or a shared secret; cap body size; rate-limit by IP; sanitize stored fields.

**[P0] `/api/auth/change-password` — new password stored in PLAINTEXT in `profiles.password_hint`** ✅
File: `src/app/api/auth/change-password/route.ts:61`
Risk: Line 56 comment says "clear password_hint", but line 61 does `password_hint: newPassword, // Store plaintext for admin reference`. Every user's live password is written cleartext to the DB, readable by any DB/service-role access or any route selecting `profiles`. Defeats password hashing entirely.
Fix: Delete the `password_hint: newPassword` write; persist only `password_changed_at`.

**[P0] `/api/users/[id]/password` — admin/boss can reset ANY user's password (incl. boss), no audit, self-change skips current password** ✅
File: `src/app/api/users/[id]/password/route.ts:77-88, 91-100`
Risk: `adminClient.auth.admin.updateUserById(targetId, {password})` (line 99) has no target-role check → an `admin` can reset the `boss` password (silent account takeover) with no audit row. The self-change branch (`targetId === "change-password"`, lines 77-88) calls `supabase.auth.updateUser({password})` without verifying the current password — a stolen session can lock out the real user (the sibling `/api/auth/change-password` *does* verify old password).
Fix: Forbid resetting roles `>=` caller's role; block self-reset (force `change-password` flow); require+verify `oldPassword` in the self branch; write an audit row.

**[P0] `/api/leads/[id]/milestone` — IDOR: any authenticated user completes milestones / sets won|lost on ANY lead** ✅
File: `src/app/api/leads/[id]/milestone/route.ts:41-121`
Risk: Fetches the lead only to check existence (line 41); never checks `assigned_to === user.id`. A `sales` user can POST `milestoneKey:"won"` against a colleague's lead and set its `final_status` (lines 109-121), corrupting pipeline/commissions. (RLS is the only backstop; the code does no app-level authz.)
Fix: Before insert, enforce `isAdmin || lead.assigned_to === user.id`.

**[P0] `/api/leads/[id]/follow-up` — IDOR: any user writes follow-up logs to any lead** 👁
File: `src/app/api/leads/[id]/follow-up/route.ts:76-103`
Risk: Lead is fetched only to confirm existence; caller assignment never verified. Any sales user injects `follow_up_logs` (+ auto-created tasks via trigger) into other reps' leads — timeline poisoning.
Fix: Add `lead.assigned_to === user.id` (or admin/manager) check before insert.

**[P0] `/api/quotations/generate` — service_role writes to ANY `lead_id`; no ownership check** 👁 (service-role grep confirms key usage)
File: `src/app/api/quotations/generate/route.ts:91-175`
Risk: After only `getUser()`, uses service_role to insert quotation/activity/business_event **and mutate the lead's stage to `quotation_submitted`** (line 166) for an arbitrary, non-owned `lead_id`. Because writes are service_role, RLS cannot rescue it.
Fix: Route all writes through `createServerSupabase()`; verify `lead.assigned_to === user.id` or admin/boss first.

**[P0] `/api/hermes/generate-quote` — service_role writes to any lead_id** 👁
File: `src/app/api/hermes/generate-quote/route.ts:139-178, 194-312`
Risk: All DB access (profile, lead, quotation insert, activity/event inserts, lead-stage mutation) via service_role. The only guard (`sales && assigned_to !== user.id`, line 176) doesn't cover operator/admin paths. IDOR + unauthorized state mutation, RLS-defeated.
Fix: Move writes to user-auth client; restrict non-owning access to admin/boss.

**[P0] `/api/hermes/knx-design` — service_role + unbounded outbound HTTP + fire-and-forget background pipeline on any lead** 👁
File: `src/app/api/hermes/knx-design/route.ts:130-258, 267-316`
Risk: After `getUser()`, enqueues a background pipeline that re-derives `supabaseAdmin` itself (line 132), calls out to `HERMES_BRIDGE_URL/api/knx-system-plan` (line 145), and upserts `knx_designs` as service_role. Any authed user can spawn unbounded external calls/rows against any `lead_id`; the pipeline keeps running after auth expiry.
Fix: Authorize before enqueue; gate to assigned-sales/admin/boss; cap concurrency per user.

**[P0] `/api/cron/check-overdue-followups` — CRON_SECRET passed as `?token=` query param (leaks in logs) + uses the anon/no-session client** ✅
File: `src/app/api/cron/check-overdue-followups/route.ts:13-23`
Risk: Unlike every other cron route (which use the `x-cron-secret` header), this one reads `searchParams.get("token")` (line 18) — query strings land in server access logs, proxy logs, and referer headers, exposing the shared secret. It also calls `createServerSupabase()` (line 23), which under a cron call has no session cookie → the `tasks` select and `notifications` inserts run as anon and likely fail/silently no-op under RLS. Double defect.
Fix: Switch to the `x-cron-secret` header and use `supabaseAdmin` (consistent with the other 6 cron routes).

**[P0] `/api/activities` — no authorization scoping; returns any lead's / the global activity feed** ✅
File: `src/app/api/activities/route.ts:9-38`
Risk: After `getUser()`, no `user_id`/`assigned_to` filter. `?lead_id=X` returns that lead's full activity history to whoever is logged in; with no `lead_id` it returns the global stream. (Stale header comment claims "bypasses RLS via service role", but the code uses the user-auth client — so RLS is the *only* backstop; if policies are permissive this is a full horizontal privilege escalation.)
Fix: Resolve lead ownership / scope by the caller's own leads before returning rows.

## P1 — Unnecessary service_role / weak validation / IDOR reads

- **`/api/notify` (+ shared `src/lib/notifications.ts`)** 👁 — inserts notifications via `supabaseAdmin` from a *user* route, defeating RLS; most branches (`lead_created`, `quote_created`, `contract_*`, `followup_reminder`, `follow_up_overdue`, `first_payment_reminder`) accept caller-supplied ids with **no ownership check** → any user can spoof notifications (with customer names/amounts) into peers' inboxes. Only `payment_received` checks ownership. Fix: insert via user-auth client; mirror `payment_received`'s ownership check in every branch.
- **`/api/follow-ups?lead_id=`** 👁 `src/app/api/follow-ups/route.ts:37-49` — IDOR read: any user reads any lead's follow-up history (call notes, contact types). Fix: verify `assigned_to === user.id` or management when `lead_id` given.
- **`/api/quotations/export`** 👁 `…/export/route.ts:55-83` — unnecessary `getSupabaseAdmin()` for a read that's already ownership-scoped; widens blast radius. Fix: use user-auth client, let RLS enforce.
- **`/api/quotations/[id]/convert`** 👁 `…/[id]/convert/route.ts:62-68, 166-182` — sales who created a quote can self-approve its conversion into a contract and set `final_status:"won"` (no independent approver); also fires an internal `fetch('/api/notify')` with **no auth header**. Fix: admin/boss-only approver distinct from `created_by`; forward auth or call notify in-process.
- **`/api/hermes/knx-design/status`** 👁 — IDOR on `task_id`: any user polls any task's result payload (devices, totals, lead_id). Fix: verify task initiator before returning.
- **`/api/kpi/targets` GET** 👁 `…/kpi/targets/route.ts:6-24` — only `getUser()`, no role gate; any user dumps every employee's KPI targets + full names (POST/DELETE are correctly gated). Fix: add the same role gate as POST.
- **`/api/users` POST** 👁 `…/users/route.ts:121-126` — `sales` role may create new auth accounts (privilege normally admin-only). Fix: restrict POST to admin/boss.
- **`/api/users` (GET/POST)** 👁 — unnecessary `supabaseAdmin` after the role gate; only `auth.admin.createUser` truly needs it. Fix: run profile reads/inserts on user-auth client + RLS.
- **`/api/activity/daily-report`** 👁 `…/daily-report/route.ts:57-70,105` — after a correct `checkAdminOrBoss` gate, reads via `supabaseAdmin`; service_role unnecessary (caller already has a valid Bearer token). Fix: use the user-auth client.
- **`/api/dashboard/ads-roi/import`** 👁 `…/ads-roi/import/route.ts:31-50` — `execFile("python3",…,{ env:{...process.env} })` leaks `SUPABASE_SERVICE_ROLE_KEY` to the subprocess; no audit log on bulk insert. Fix: pass minimal env; write a `business_events` row.
- **`/api/dashboard/sales-load/rebalance`** 👁 `…/rebalance/route.ts:6-115` — correctly admin/boss-gated, but per-row `await` updates with no transaction (partial-failure leaves leads half-reassigned) and no audit trail of the mass ownership transfer. Fix: single transaction/RPC; emit audit rows.
- **`/api/dashboard/team-ownership`** 👁 `…/team-ownership/route.ts:5-58` — `getUser()` but **no role check**; any user (incl. `sales`) receives the full team-wide lead-ownership/win-loss breakdown. Fix: 403 unless admin/boss/operator.
- **`/api/leads/meta-capi`** 👁 `…/meta-capi/route.ts:32` — webhook secret compared with non-constant-time `!==`. Fix: `crypto.timingSafeEqual`.

## P2 — Hardening (audit log / rate limit / hygiene)

- **All cron routes**: secret compared with `!==` (timing-unsafe); use `crypto.timingSafeEqual`.
- **`/api/leads/meta-capi`**: no rate limit / replay protection / idempotency key.
- **`/api/leads/archive`** (`…/archive/route.ts:23-41`): bulk destructive op, no audit row recording who/why.
- **`/api/leads/import/confirm`**: no upper bound on `rows.length` → unbounded write amplification; should also be role-restricted.
- **`/api/notify`**: no rate limit; `createNotificationsBulk` fans out to all users.
- **`/api/cos/download-url`**: `expires` is caller-controlled with no upper bound (near-permanent URLs); presign not rate-limited/audited.
- **`/api/dashboard/pipeline-funnel`** (`:173-180`): broken `.eq("lead_id", supabase.rpc(...))` filter (`.eq` needs a scalar) → sales silently get empty `lostFromStage`; swallowed error. Correctness defect.
- **`/api/health`**: unauth liveness probe that nonetheless runs a real DB query + REST round-trip and exposes version/memory/build-id; scope to internal/LB.
- **`/api/users` POST / `/api/users/[id]` DELETE**: no audit log of account provisioning/deletion.
- **`/api/dashboard/ads-roi`**: returns raw `err.message` when `NODE_ENV !== "production"`.
- **`/api/hermes/*` & `/api/quotations/generate`**: no rate limiting; quote-number allocation (`generateQuoteNo`) has a read-modify-write race; `quotations`/`knx_designs` rows omit `created_by` provenance.
- **`/api/admin/impersonate`**: otherwise correctly gated (role check + audit log) but no rate limiting.

## Verdict: 🔴 NO-GO for production

**11 P0 findings** spanning all five audit dimensions: an IDOR over every file in object storage (`cos/download-url`), plaintext password storage (`auth/change-password`), invisible privilege escalation via password reset (`users/[id]/password`), a fully unauthenticated disk-write endpoint (`monitoring/report`), a cron secret leaked via URL query param (`check-overdue-followups`), and service_role write paths that defeat RLS to let any user mutate any lead (`quotations/generate`, `hermes/*`, `leads/[id]/{milestone,follow-up}`). Several are trivially exploitable by a low-privilege `sales` account.

**Minimum to reach GO:** (1) remove the `password_hint` plaintext write; (2) add ownership checks + drop service_role on the quotation/hermes/leads write paths; (3) gate `cos/download-url` by object ownership; (4) authenticate `monitoring/report`; (5) fix the cron `?token=`→header + client bug; (6) add target-role + audit + current-password to `users/[id]/password`; (7) scope `activities` and `kpi/targets` GET. P1/P2 hardening (rate limits, audit logs, constant-time compares) should follow but the P0 set alone blocks ship.
