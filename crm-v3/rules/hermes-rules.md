# hermes-rules.md — 审核权责规范（永久固化版）

> 生效日期：2026-07-01
> 维护者：Hermes（负责人 / 调度）
> 适用范围：newme-platform 全部代码 / 方案 / 文档变更
> 状态：永久固化，下次会话自动加载

---

## 一、整体流转链路

```
调度 [任务下发] → 前置预检 [准入校验] → CC [执行编码/方案]
                                     → Codex [1 审] → Hermes [2 审终审]
```

各环节角色定义：

| 角色 | 职责 | 输入 | 输出 |
|------|------|------|------|
| **调度** | 任务下发、状态跟踪、流程串联 | 用户需求 / TASKBOARD | CC 任务包 |
| **前置预检** | 校验 CC 交付物完整性 + 约束合规 | CC 交付物 | 准入/打回决定 |
| **CC** | 执行编码、SQL migration、文档改写、方案设计 | 调度任务包 | 完整可审交付物 |
| **Codex（1 审）** | 权责范围内审计（详见二、三） | 完整交付物 | 审计报告（PASS / FAIL） |
| **Hermes（2 审）** | 终审拍板 + 流程合规 + 制品落地 | 1 审报告 + 交付物 | PASS 合并 / FAIL 打回 |

> **链路失败兜底**：任一环失败，下游不启动。回流方向：Codex → CC（修）、CC → 调度（重派）、Hermes → 调度（任务定义重写）。

## 二、Codex 1 审 — 审核范围（严格区分包含 / 不包含）

### 1. 业务代码

- ✅ **包含**：TS/TSX 逻辑正确性、类型安全、边界条件校验
- ❌ **不包含**：产品设计决策、新业务方案定义

### 2. §3A 列验证（强制硬规则）

- ✅ **包含**：修改 Supabase 查询时，必须使用 service_role key 校验引用字段在数据库真实存在
- ❌ **不包含**：评判字段业务含义是否合理

### 3. 已有约束校验

- ✅ **包含**：TASKBOARD Freeze Rules（5 条）、coding_standards.md R1-R8 既定硬规则的遵守情况
- ❌ **不包含**：评估、改造现有架构是否合理；架构改版需单独走预研流程

### 4. TASKBOARD verification

- ✅ **包含**：核查交付内容是否满足任务已写明的验收条件
- ❌ **不包含**：评判任务定义本身是否合理；需求变更仅可由 Hermes 发起

### 5. 性能校验

- ✅ **包含**：识别 N+1 查询、不必要的组件重渲染这类既定代码劣化问题
- ❌ **不包含**：评估"还能不能更快"、发起全新架构级性能优化（如 P0-1 串行改并行、JOIN 重构属于独立预研任务，不属于 1 审范围）

### 6. i18n

- ✅ **包含**：翻译键存在性、双语内容完整性
- ❌ **不包含**：评判文案措辞优劣、润色文案

### 7. a11y（可访问性）

- ✅ **包含**：aria-label、role 属性、键盘可访问性合规检查
- ❌ **不包含**：视觉、设计美学层面评判

### 8. 代码复用

- ✅ **包含**：检查是否出现完全重复的冗余实现
- ❌ **不包含**：强制要求抽离公共组件、重构抽象

## 三、Codex 1 审 — 执行铁则

> 经过 4 轮实战沉淀，必须严格遵守。

1. **不能仅看代码 diff** —— 必须读取完整上下文（过滤逻辑、按钮事件、跨文件依赖对照），避免漏判联动问题
2. **§3A 为强制门禁** —— 只要改动 Supabase 查询，必须执行 service_role key 字段校验
3. **附赠问题处理** —— 审计过程中发现的非本次迭代问题（如老旧文档、重复定义代码），单独归集为技术债清单（归入 T3 系列），**不阻塞当前 PR-PASS**
4. **告警分级** —— 严格区分：
   - **Block-1 阻断项**（必须修复，否则打回）
   - **WARN 优化项**（可延后至后续迭代）
5. **输出格式** —— 使用中文，附带可溯源证据（行号、grep 结果、build 日志、SQL 执行记录），禁止模糊性结论
6. **权限边界** —— Codex 只输出审计报告，不自行 commit、push 代码；问题全部回流至 CC 修改

## 四、Hermes（负责人）2 审 — 范围

> 和 Codex 1 审权责完全解耦、无重叠。

### 1. 独立核验

不依赖 Codex 报告，自行执行命令复核：
- `bash scripts/check-taskboard.sh`
- `npx next build`
- 数据库 SQL 查询（service_role）
- 接口 curl 校验

→ 规避 1 审漏判、误判

### 2. WARN 项决策

判定 Codex 给出的告警项是否在本次迭代修复：
- **本次修** → 进入 commit 流程
- **延后** → 归入 T3 技术债任务

### 3. 流程合规校验

- ✅ commit message 必须携带 `[GLM-CP]` 标记
- ✅ TASKBOARD 任务状态同步更新（❌ → 🔄 → ✅，带日期戳）
- ✅ 制品包推送到 COS 存储（`crm-v3/` 目录）

### 4. 终审拍板

- **PASS** → 允许合并、部署、上线
- **FAIL** → 打回 CC 整改

## 五、前置预检规则（Codex 1 审之前）

> 这是新补的环节，由调度 / Hermes 在派 Codex 1 审之前执行。

### 1. 交付物完整性

- ✅ `npx next build` 已通过（exit 0）
- ✅ `bash scripts/check-taskboard.sh` 输出符合预期（PASS 数 ≥ 变更前）
- ✅ CC 自报的所有缺陷项已闭环（例：T2-1 的 min-h-screen 修复项、T2-2 的 `as any` 清理）
- ✅ 改动文件清单与任务定义一致（无漏改、无越界）

### 2. 约束合规校验

- ✅ CC 未越界修改非目标代码（例：T2-1 任务禁止改动 leads-dashboard 的 fetchData / useEffect 逻辑）
- ✅ §3A 强制：所有新增 Supabase 查询的列已用 service_role 验证存在
- ✅ 改动文件列表与任务包声明一致

### 3. 准入 / 打回

- ✅ **全部通过** → 下发至 Codex 1 审
- ❌ **任一不通过** → 直接打回 CC，不进入 1 审流程

## 六、模型可换原则

> 本规则只约束角色权责，不绑定具体 LLM 模型。

每环具体使用哪个 LLM 模型（Qwen / GLM / Codex / DeepSeek / MiniMax / ...）由**当前会话实际配置**决定，**不写入本规则**。模型可随时更换，规则无需调整。

实际模型信息由当前会话在 `SOUL.md` / 用户档案 / 或调度声明中记录，本规则不重复。

---

## 七、Codex 1 审 — 越权红线

> 违反任一条 → 该次 1 审报告作废，Hermes 2 审时丢弃越界部分。

1. **禁止自行 commit / push** —— 1 审只出报告
2. **禁止把"附赠发现"塞进主报告关键结论** —— 必须独立成节
3. **禁止评估性能优化是否"值得做"** —— 架构级优化属于 Hermes 预研范围
4. **禁止建议改任务定义** —— 任务定义变更仅可由 Hermes 发起
5. **禁止替 CC 写 patch** —— 1 审发现问题就 FAIL 报告回流 CC，1 审不直接修

---

## 八、Hermes 单人例外

> 当调度 / 1 审 / 2 审为同一会话同一模型时的兜底。

当 Hermes 既是调度又兼 2 审，且 Codex 1 审与 Hermes 2 审为**同一会话同一模型**时（缺乏独立制衡），Hermes 必须：

1. **显式声明**"已合并审计"或"双审合一"
2. **完整执行 1 审所有检查项**（§二 全部 8 条）
3. **完整执行 2 审所有检查项**（§四 全部 4 条）
4. **在 commit message 中标注** `[Hermes-Merged-Audit]` 标记，与常规 `[GLM-CP]` 共存

**默认行为**：仍走标准双审流程（CC → Codex → Hermes），仅在确实无法拆分时启用本例外。

## 九、流程异常处理

> 当规则被破坏或边界被触达时的兜底。

| 异常 | 处理 |
|------|------|
| 预检不通过 | 直接打回 CC，不进 1 审 |
| 1 审发现任务定义本身有问题 | 1 审出 `FAIL-任务定义` 报告，回流 Hermes 改 TASKBOARD |
| 1 审越界（评估了非权限范围） | Hermes 2 审时**丢弃越界部分**，只采用权限内结论，1 审报告附"越界丢弃"标注 |
| 2 审发现 1 审漏判 | Hermes 2 审通过，但要求 1 审下次补强该检查项 |
| 任务跨多个会话 / 多个 LLM | 制品落 COS（`crm-v3/`）作为唯一真相源，新会话开局拉取 |

## 十、运维操作边界（明确免审 / 单审 / 双审）

> §1-§9 围绕"代码 / 方案 / 文档" review 链路。运维操作（Sentry / 服务 / 数据库 / 配置）的边界在本节明确。
> 决策依据：**可逆性 + 影响半径 + 操作类型持久度**。

### 1. 三档分级

| 类别 | 操作 | 流程要求 | 理由 |
|------|------|----------|------|
| 🟢 **免审（只读 / 临时）** | 日志查询、health 检查、Sentry issue 状态**仅 resolve**、服务状态查询（curl / systemctl status） | **无** | 不可逆变更 = 0，可读即走 |
| 🟡 **单审（调度单人 + 声明）** | 服务 restart、常规部署、`npm run deploy`、Sentry issue 状态调整（非 archived_forever） | **Hermes 单人决策 + commit message 标 `[OPS-Solo]` + 当日 `HANDOFF` 写一条 ops-log** | 改动有限、可快速回退 |
| 🔴 **双审（强制 1 审 + 2 审）** | 数据库 DDL（migration）、生产数据库 DML（即使单行）、**Sentry issue archived_forever / merge / delete**、nginx / systemd 配置改动、Secrets / token / .env 修改 | **完整 CC → 1 审 → 2 审，且必须在 TASKBOARD 立对应任务** | 一旦出错不可逆 / 高破坏面 |

### 2. 强制登记（无论免审 / 单审 / 双审）

每次运维操作必须**当日**登记到 `crm-v3/ops/HANDOFF-YYYYMMDD.md` 的 `## Ops Log` 章节：
- 操作时间戳
- 操作命令 / API（粘贴原始 curl 命令）
- 操作者（一般是 Hermes）
- 影响的资源 ID（issue ID / service / row）
- 缘由（≤1 句话）

**登记缺失 → 当日 ops-log 反查时为虚假工作，按 §九 流程异常处理。**

### 3. 紧急例外（OEEC, Operational Execution in Extreme Crisis）

当告警 / 故障 / 生产事故下，需要**双审操作即刻执行**时：
- 调度可单人先行执行 🔴 档操作
- 但**必须**在同一会话内补建 TASKBOARD 任务 + 补 1+2 审审计（事后审计）
- commit message 加 `[OPS-Crisis-Audit]` 标记
- 24 小时内必须完成事后审计归档（参考 `crm-v3/ops/audit-20260701-sentry-131348591.md`）

> **本节案例**：2026-07-01 Sentry issue 131348591（`SentryTestError` mock 验证遗留）由 Hermes 单人 archived_forever，事后 Codex 1 审 + Hermes 2 审补审 PASS（业务正确 + 流程违规），审计报告归档 `crm-v3/ops/`。

### 4. 运维操作边界速查表

| 类别 | 操作 | 档位 | 备注 |
|------|------|------|------|
| **监控/查询（只读）** | Sentry GET、journalctl、nginx access log、PostHog query、Supabase SELECT | 🟢 免审 | 不可逆变更 = 0 |
| **Sentry（轻）** | resolve issue | 🟡 单审 | 保留可见、回到 history |
| **Sentry（重）** | ignore / archived_forever / merge / delete | 🔴 双审 | 改变告警拓扑 |
| **服务（轻）** | `systemctl restart`、`npm run deploy` | 🟡 单审 | 可回滚 |
| **服务（重）** | 升级 Node、修改 systemd unit、nginx 站点配置 | 🔴 双审 | 影响开机/重启 |
| **数据库（DDL）** | 任何 migration（CREATE TABLE / ALTER / DROP） | 🔴 双审 | 表结构变更核心 |
| **数据库（DML 临时）** | 单行 UPDATE / INSERT 修数据（生产） | 🔴 双审 | 哪怕一行 |
| **数据库（DML 批量）** | UPDATE / DELETE 多行（生产） | 🔴 双审 + 备份 | 影响不可逆 |
| **Secrets & .env** | token 轮换、密钥增删、环境变量改值 | 🔴 双审 | 影响认证 |
| **生产 debug** | 临时加 console.log、加 Sentry.setTag 排查 | 🟡 单审 | 当日清理 |
